# Security and Privacy Reference

Thoughty stores private journals, attachments, sessions, and encrypted third-party credentials. This page lists the rules the code enforces and new code must keep. Decisions are in [ADR 0008](./adr/0008-security-authentication-and-owasp-baseline.md) and [ADR 0009](./adr/0009-rate-limiting-and-abuse-controls.md).

## Baseline

- Every API route needs an access token unless marked `@Public()`.
- The global `ValidationPipe` whitelists DTO fields and rejects unknown ones. It converts no value implicitly: a text must arrive as a string, and booleans and numbers are read strictly by `@StrictBoolean()` and `@StrictInt()`, so `""`, `1.5` or `true` sent for an ID is a 400 instead of becoming `0` or `1` ([Request validation](./development.md#request-validation)).
- Every query is scoped to the authenticated user. A diary, entry, or attachment the caller does not own answers `404`, including the target diary when creating, moving, or importing entries.
- Passwords use bcrypt. Every password a writer chooses (sign-up, reset, change) follows one rule, `@StrongPassword()`: 8 characters or more with an uppercase and a lowercase letter, a digit and one of `!@#$%^&*(),.?":{}|<>`. Breaking only that rule answers `400 AUTH_WEAK_PASSWORD` (the global validation pipe reads the code from the constraint's `context`); the web checks the same rule first (`isStrongPassword`) and states it under each such field. Sign-up, reset, verification, and 2FA challenge tokens are stored only as SHA-256 hashes.
- In production, API responses carry a per-response nonce CSP with no `unsafe-inline` (`common/security/csp.ts`), and served HTML such as Swagger UI gets the nonce. Do not add `unsafe-inline`.
- The web NGINX config (`thoughty-web/nginx-security-headers.conf`, included for every response including `/assets/`) sends a strict CSP: scripts, styles, fonts, and connections from `'self'` only, images from `'self'`, `data:`, `blob:`, and Google profile pictures, media and frames from `blob:` for attachment previews (audio and video players included), `object-src 'none'`, and `frame-ancestors 'none'`. Only style attributes are allowed inline, because the browser's own PDF and text viewers need them. External images in Markdown entries are therefore blocked. It also sends HSTS, `X-Frame-Options: DENY`, and a `Permissions-Policy` that allows only the microphone (memoir recordings). The easy-to-read font (Atkinson Hyperlegible) stays within it: it is an npm dependency (`@fontsource/atkinson-hyperlegible`) bundled by Vite into `/assets/`, so `font-src 'self'` covers it and no font host is contacted. The share-as-image card stays within this policy: it is drawn on a canvas from the entry text, system fonts, and the app's own same-origin logo (so the canvas is never tainted), and leaves only as a `blob:` download, a clipboard copy, or the Web Share API, neither of which the `Permissions-Policy` turns off for the app's own origin. The book preview stays within it too ([ADR 0021](./adr/0021-in-app-book-preview-with-pdfjs.md)): PDF.js is a pinned dependency bundled with the app, its worker is a same-origin script under `script-src 'self'` (no `blob:` worker, no `eval`), the PDF is read from memory and drawn on a canvas, and it fetches nothing at run time (no WebAssembly, CMaps or standard font files). A build with `VITE_GOOGLE_CLIENT_ID` set would also need the Google Identity Services origins added to the CSP.

## Authentication and Sessions

Thoughty accepts two kinds of accounts side by side, in every environment: local accounts (email or username and password, registered in the app) and, in production, Keycloak single sign-on. The sign-in and sign-up pages show both. **Continue with SSO** opens the platform's Keycloak sign-in (`https://keycloak.swirlit.dev/oauth2/start`) and returns to the app, which then calls `GET /api/auth/sso` once; a visitor is never sent to Keycloak unasked. Only that route goes through the platform's Keycloak OAuth2 Proxy (the `thoughty-sso` ForwardAuth Middleware on its own ingress), which forwards the Keycloak access token. The rest of `/api` is reachable without Keycloak and authenticates every request itself. The API verifies its RS256 signature against Keycloak's JWKS, plus issuer, expiry, and the `oauth2-proxy` audience, and requires a verified email. It then signs in, links or creates the account (see **Linking Google and Keycloak identities** below) and issues Thoughty's own tokens. The Middleware only obtains the token; the signature check is the security boundary, so identity headers are never trusted unverified. Signing out of a Keycloak account also ends the Keycloak session; signing out of a local account does not. Google sign-in is optional: the browser sends the Google ID token and the API verifies its RS256 signature against Google's keys, the issuer, the audience (`GOOGLE_CLIENT_ID`, which must match the web's `VITE_GOOGLE_CLIENT_ID`), and expiry, and requires a verified email before it links or creates the account. Without `GOOGLE_CLIENT_ID` Google sign-in answers `503`. Both flows share `auth/services/jwks-key-store.ts`.

- **Access token:** JWT signed with `JWT_SECRET`, 15 minutes by default (`JWT_EXPIRES_IN`).
- **Refresh token:** JWT signed with `REFRESH_SECRET`, valid 7 days. Only its SHA-256 hash is stored, in `refresh_tokens`; each row is a session. Every refresh deletes the presented row and issues a new token, so a token works once and a replayed one answers `401`.
- **Where tokens live:** the refresh token travels only in the `thoughty_refresh_token` cookie (httpOnly, `SameSite=Strict`, `Secure` in production, path `/api/auth`), set by every endpoint that signs in and cleared on logout, account deletion, and a rejected refresh. No response body contains it, and no request body is read for it: refresh, logout and session management take the token from the cookie alone, so a token sent in a body is ignored and refresh answers `401` `AUTH_REFRESH_TOKEN_MISSING`. The web app keeps the access token in memory and calls refresh on page load. It never uses `localStorage` for tokens; on load it deletes the `accessToken` and `refreshToken` keys that versions before the cookie left there, without sending them.
- **When a session ends in the web app:** every way one ends goes through `endSession` (`contexts/useAuthSession.ts`): **Logout**, account deletion, a refresh the server refuses (`401` or `403`: an expired or revoked refresh token, which is how a password change, a reset elsewhere or **Sign out other sessions** in another browser reach this one, or a deleted account; a refresh that reaches no working API, gets a `429` or any other answer ends nothing, see Journal opened offline under Data Protection), `GET /api/auth/me` refusing the token (`401` or `403`; a token held since an earlier try is refreshed once first, since it may just have expired; a `429`, a `5xx`, an answer that cannot be read or none at all ends nothing, see Journal opened offline), another tab of the browser signing out, and another writer signing in over this one (in this tab, or in another tab, since the cookie is then theirs). It drops the access token, the tab's PIN unlock and the writer remembered for an offline start, and moves `sessionKey` on. The app keys its React Query cache (`useSessionQueryClient`: a new, empty `QueryClient` in the same render, the old one's requests cancelled and its contents cleared) and the whole tree under the router on that key, so every piece of the writer's state goes with it: cached entries, diaries, settings (theme and language included, so signed-out pages look and read as for any visitor), people, the composer, filters, open dialogs. A request or callback that outlived the session can only write into the old cache, which nothing reads. A refresh answered after its session ended is not used, a `401` refreshes only for a request sent with a token in a session still on, so nothing is asked again with the old credentials, and ending the PIN unlock with the session reads nothing again. Logout ends the session in the page at once, before the server answers, then revokes the cookie under the cross-tab refresh lock, so it revokes the cookie a refresh in flight has just set. Logout and account deletion remove this browser's composer draft copies and tell the other tabs (`BroadcastChannel` `thoughty.auth-session`, same origin, messages checked); a session that ends by itself keeps the device's copy (keyed by account), since it may hold text the server does not have yet, and a draft save answered after the composer is gone writes nothing to the device. The password reset page keeps its outcome in the history entry, so it still says the reset is done once signing out has started the page again.
- Users can list sessions (token values are never returned) and revoke one or all others. Logout deletes the presented token. Password change, password reset, and account deletion delete all of them.
- **Account activity** (**Profile › Privacy**, `GET /api/auth/activity`, `auth/account-activity`): one `account_events` row per sign-in (password, two-factor, Google, Keycloak, completed sign-up; a token refresh is not one), refused sign-in (a wrong password for a live account with a password, or a wrong sign-in code; an unknown, deleted or password-less account records nothing, and the answer is the same either way), sign-out, other sessions signed out, password change and reset, two-factor turned on or off, PIN set, changed, reset or removed, data download, journal export, and private share link made or revoked. Each row keeps only the kind, the time and the browser and system *names* read from the `User-Agent` header by `ClientSoftwareMiddleware` (`parseUserAgent`: no version, no IP address, nothing else of the header; a header over 1,000 characters is not read). Rows are listed only to the account (newest first, 50 a page, `before` an id), are in its data download, are removed after a year by the worker, and go with the account. A recording failure is logged with the kind only and never fails the action it records. Account email cannot be changed in the app, so there is no email-change event yet.
- **Personal access tokens** (`modules/access-tokens`, **Profile › Access tokens**): `thy_` and 32 random bytes in URL-safe base64, shown once; only the SHA-256 (`token_hash`, never selected) and the first eight characters (`token_hint`) are kept. Each holds scopes (`entries:read`, `entries:write`, at least one) and an expiry of 30, 90 or 365 days or none; a writer holds ten at most (`ACCESS_TOKEN_LIMIT_REACHED`, counted under a per-writer advisory lock after deleting expired ones). Tokens open only the public API under `/api/v1` (`@AccessTokenScopes`, `AccessTokenGuard`): the routes are public to the session guard, and the token guard answers 401 `ACCESS_TOKEN_INVALID` without a token, for one that is unknown, revoked or expired, for a session's JWT, or for an account being deleted (`deleted_at` set), and 403 `ACCESS_TOKEN_SCOPE_MISSING` without one of the route's scopes. A token is refused everywhere else (the JWT guard does not read it), so it can never reach settings, sessions, exports, the PIN or the token routes themselves, which need a session. Entries written through it are always private (no `visibility` or `seal` is accepted), and its reads run without any PIN unlock (`runWithoutUnlock`), so locked entries stay withheld. `last_used_at` is written at most once a minute. Making and revoking a token are recorded in the account activity (`access_token_created`, `access_token_revoked`); deleting the account deletes its tokens; rate limits are the API's default per address, and 30 creations or revocations per 15 minutes. A password change or **Sign out other sessions** does not revoke tokens: revoke them in **Profile › Access tokens**.
- **New-browser sign-in email:** a sign-in from a browser and system the account has not signed in from in the past year (and not the account's first sign-in) sends an email, unless the writer turned it off (setting `newBrowserSignInEmail`, written only by `PUT /api/auth/activity/new-browser-email`). It is sent after the answer, holds the browser and system names, the time in UTC and a link to the Profile, never journal text, and a failure is logged with the user ID and SMTP reply code only. The check and the sign-in's record run under a per-account advisory lock (`account_sign_ins`), so two sign-ins at once from the same new browser send one email, and closing the application (`app.close()`, `beforeApplicationShutdown`) waits for the emails still being sent.
- Login answers an unknown, deleted, or password-less account exactly like a wrong password, after the same bcrypt work. Forgot-password returns the same message for every address after the same work (the account lookup): it stores a local account's reset token and emails the link after answering, so neither the database write nor the mail server makes an existing account answer slower. Registration answers every address the same way (see **Verify-first sign-up** below).
- Account deletion signs the writer out at once (local accounts confirm the password). A worker job erases the account and everything it owns after `ACCOUNT_PURGE_AFTER_DAYS` (default 30), see [Data Protection](#data-protection).

**Linking Google and Keycloak identities.** Both providers' identities go through `ProviderAccountService` (`auth/services/provider-account.service.ts`), and only with an address the provider asserts is verified: a Google ID token or Keycloak token whose `email_verified` claim is not `true` is refused before any account is looked up (`401 AUTH_GOOGLE_EMAIL_UNVERIFIED`, `401 AUTH_KEYCLOAK_IDENTITY_INCOMPLETE`), so an unverified provider address never links. The account is found first by the provider's subject (`users.auth_provider` and `users.provider_id`, stored at the first link or sign-up), so an account keeps signing in when its provider address changes; only when no account has that subject is the account with the same address used, and linked to the subject from then on. An account holds one provider link at a time: signing in with the other provider moves the link to it (by the verified address, as at the first link). A deleted account answers `403 AUTH_ACCOUNT_DELETED` either way.
- **A verified account** with the address is linked and changes nothing else: its owner proved the address, so their password, two-factor setting and sessions stay, and either sign-in works.
- **An unverified account** with the address is taken over for the provider's user, who has just proven the address that its registrant never did. That registrant may be someone else: before verify-first sign-up, or on a server without email, anyone could register a victim's address with their own password and wait for the victim to sign in with Google (the "pre-hijacked account" attack). So, in one transaction, the address is marked verified and the account is linked, and every way in the registrant set up is dropped: the password hash is cleared, two-factor sign-in is turned off and a pending challenge cleared, pending verification and reset links and any sign-up request for the address are deleted, every refresh token (every session) is revoked, and cloud backup connections and their schedules (`cloud_*` settings) are removed, as a drive the registrant connected would otherwise keep receiving the owner's backups. Then the provider's user is signed in. The diaries and entries stay: the registrant is just as likely to be the owner, who once registered and never opened the verification email, and who keeps their journal. An access token already issued to the registrant stays valid until it expires (15 minutes by default), as after a password reset. The owner signs in with the provider from then on; refusing the link until the address is verified was the alternative, but it would lock the real owner out wherever no email can be sent and give them no way to recover the account, while the registrant's password kept working.
- **A new account** is verified at once, gets its default diary, and is named as the provider suggests (the Google name, the Keycloak `preferred_username`, or the part of the address before the `@`; markup stripped, cut to 50 characters), with a random six-digit number when another account has the name in any case (`freeUsername`, shared with sign-up; usernames are unique ignoring case, see [Data model](data-model.md#usernames-and-addresses)). The account and its diary are created in one transaction; when a sign-in racing it takes the name or creates the account first (PostgreSQL unique violation `23505`), the sign-in looks again (taking another name, or finding the account the other request created), up to three times, and then answers `409 AUTH_USERNAME_TAKEN` or `409 AUTH_EMAIL_TAKEN` rather than a `500`.

**Verify-first sign-up.** Wherever the server can send email, `POST /api/auth/register` creates no account and answers every address with the same `202` and body (`{ verificationRequired: true, message }`), no cookie, after the same work: the password is bcrypt-hashed and the address looked up and recorded for both kinds, and the email is sent in the background, as forgot-password does (`auth/services/sign-up.service.ts`). A new address gets a link to `/complete-sign-up?token=…`; one that already has an account gets a notice instead ("someone tried to sign up with this address: sign in, or use **Forgot password?**"), with no link to act on, and its account is not touched. A deleted account waiting for its purge gets nothing. The request waits in `sign_up_requests` (one row per lowercase address) with only the SHA-256 of the link's 32-byte random token and the bcrypt hash of the chosen password; the token itself is only in the email. `POST /api/auth/register/complete` creates the account, with a verified email and its default diary, only with that token and the same password again, so a link sent to an address someone else signed up with cannot create an account whose password that person knows (the "pre-hijacked account" attack). The link's page removes the token from the address at once and is kept out of referrers and the NGINX access log, as below for email verification. The token and the account are claimed in one transaction, so the link works once even when two requests race, and it expires after 24 hours. The username is checked only then, by someone who has proven the address: a taken one answers `409 AUTH_USERNAME_TAKEN` and keeps the link working until another is chosen; without one, the part of the address before the `@` is used, with a number if taken. Emails to one address are spaced at least a minute apart and capped at five until its request expires, whatever the IP; a request in between answers the same and changes nothing, so asking again (the web's **Send the email again**, which repeats the request) is just as silent. The worker purges expired requests hourly. Without a mail server nothing can be proven: outside production, registration then signs in at once and still reports a taken email or username (`409`, compared ignoring case, and also when a racing registration takes it first: the account and its diary are created in one transaction and the unique violation is mapped; without a username, the part of the address before the `@`, with a number if taken), for development, the e2e mock and the contract suites; in production it answers `503 EMAIL_DELIVERY_NOT_CONFIGURED` for every address, so production needs working SMTP for local sign-up ([Operations](./operations.md#email-delivery)). Google and Keycloak sign-up need a verified identity from the provider before they create or link an account, so they reveal nothing to someone without it, and linking one to an account registered before verify-first (or without email) takes the account over, as above.

**Email verification and 2FA.** Verification tokens last 24 hours. An account without a real address (a placeholder on `.invalid`, [Data model](data-model.md#accounts-without-an-address)) gives one with `POST /api/auth/add-email`; it only takes effect once the link emailed to it is opened, so no one can take an address they cannot read, and a provider address on `.invalid` is refused so it can never match a placeholder. The web page `/verify-email` reads the token from the address and removes it from the address bar and its history entry at once (`useLinkToken`), as `/complete-sign-up` and `/reset-password` do; a verification that went through is kept in the history entry's state, so a reload still shows it without the token, and any other reload asks to open the link again. The web NGINX sends all three pages with `Referrer-Policy: no-referrer` and `X-Robots-Tag` and leaves them out of its access log (`$thoughty_secret_link` in `nginx.conf`), so their tokens do not reach the requests the pages make while they load. Verified password accounts can enable email 2FA. Login then returns an opaque challenge until the six-digit code is confirmed. Codes are HMAC-SHA-256 values keyed by `TWO_FACTOR_SECRET` (derived from `JWT_SECRET` if unset; use one value across replicas). Challenges expire after 10 minutes and are cleared atomically on success. Disabling 2FA needs the password.

**Password reset.** `POST /api/auth/forgot-password` answers every address with the same `200` and message once the account is looked up. Only for a live local account does it then, in the background, store the SHA-256 of a new 32-byte random token (replacing any earlier one, so only the latest link works) and email a link to `/reset-password?token=…` that lasts one hour (`auth/services/password.service.ts`). A failure of either step is logged with the error and user ID only, never the address or the link, so production needs working SMTP. `POST /api/auth/reset-password` bcrypt-hashes the new password (the same rule as sign-up: 8 characters or more with an uppercase and a lowercase letter, a digit and one of `!@#$%^&*(),.?":{}|<>`), then in one transaction claims the link and sets the password in a single conditional `UPDATE` (the token's hash, unexpired, account not deleted), so a link works once even when two requests race, and deletes every refresh token of the account: every session is signed out. A used, expired, replaced or unknown link, and one for a deleted account, answer `400 AUTH_INVALID_RESET_TOKEN`. The reset signs nobody in, so a two-factor account still needs its emailed code to sign in afterwards, and a sign-in code asked for with the old password stops working (the pending challenge is cleared). As with signing out elsewhere, an access token already issued stays valid until it expires (15 minutes by default). The web page reads the token from the address and removes it from the address bar and its history entry at once (a reload then offers a new link), and the web NGINX sends `/reset-password…` with `Referrer-Policy: no-referrer` and `X-Robots-Tag` and leaves it out of its access log, so the token does not reach the requests the page makes while it loads. A browser signed in when the link is opened is signed out after the reset.

## Public Surfaces

`@Public()` routes: health, metrics, register and its completion (`POST /api/auth/register/complete`), login, 2FA verify and resend, OAuth, SSO, refresh, logout, forgot and reset password, verify email, the opt-in email unsubscribes (`POST /api/email-unsubscribe` and the older `POST /api/on-this-day-email/unsubscribe`), the feature-request list, the memoir question list (`GET /api/memoir/questions`: the fixed questions every memoir asks, in English and French, for the public question page; it reveals no writer data, is cacheable for an hour and has the API's default per-address rate limit), the Contact page form (`POST /api/contact`: so visitors can reach the team without an account; five messages an hour per address, a hidden bot-trap field, length limits, a name without line breaks; it reveals nothing and stores nothing, and the message goes to the deployment's own inbox as plain text, never HTML, with the visitor as reply-to), and the reader's side of private share links (`GET /api/shared/:token…`, below). A new public route must state why, which throttle applies, and what it reveals. `/api/metrics` answers only callers on the private network (Prometheus scrapes the pods directly); anyone else, including every request through the ingress, gets `404`.

Social features need a session and are refused with `503 FEATURE_DISABLED` while the `publicSharing` flag is off; then nothing becomes public either (a new public entry, a private one made public, or entries made public in bulk are refused, and imports come in private), while entries already public keep their stored visibility and are shown to no one until it is on again. They share one rule (`modules/social/public-feed-visibility.ts`): an entry is visible only if it is `public`, has `moderation_status = 'visible'`, is not archived or in the recycle bin, and its author is not deleted. Follows, comments, likes, and saves on anything else answer `404`.

- `moderation_status` is platform-controlled. No entry DTO may accept it.
- The feed returns at most 20 entries per page and leaves out mood and feelings. Authors show only `id`, `username`, `avatarUrl`, and follow state. Followers are listed only to the writer they follow (`GET /api/follows` `followers`), who can remove one (`DELETE /api/follows/followers/:userId`) without telling them.
- Self-follows, self-likes and saving your own entry answer `400`. Comments are at most 1,000 characters and render as escaped text.
- Comment controls (`PUT /api/entries/:id/comment-policy`, `PUT`/`DELETE …/comments/:commentId/hidden` and `…/pin`) answer only the entry's writer; anyone else gets `404 ENTRY_NOT_FOUND`, as for a private entry. A comment its policy refuses answers `403 COMMENTS_CLOSED` or `403 COMMENTS_FOLLOWERS_ONLY`. A hidden comment is left out of the comment list, its total and the feed's count for everyone but the entry's writer and its own writer, and liking it answers `404` to anyone else.
- The feed's topic (`tag`) and word search (`search`) only narrow the feed's own rules, so they reach only feed-eligible entries; both are bound as query parameters (the search goes through `websearch_to_tsquery`, or an escaped `ILIKE` pattern when it holds no word). Followed topics (`topic_follows`) are returned only to their reader; following a tag reveals nothing, since it matches only public entries.
- Mutes and blocks (`PUT`/`DELETE /api/writers/:userId/mute` and `…/block`, listed by `GET /api/writers/hidden`) are returned only to the writer who made them and are never shown to the writer they name. Muting or blocking yourself answers `400` (`SOCIAL_CANNOT_MUTE_SELF`, `SOCIAL_CANNOT_BLOCK_SELF`), and a writer you cannot come across in the feed, its comments or your followers answers `404 USER_NOT_FOUND`, so accounts cannot be probed. A block is read both ways on every social read and write: to each writer the other's entries, comments, follow and leaderboard place are not there (`404` on any interaction, as for a private entry), so a blocked writer cannot tell a block from an entry made private.
- A reader's Saved list (`saved_entries`) is returned only to that reader, through the feed's `saved` scope; the author is never told, and no count includes saves.
- Notifications (`GET /api/notifications`, `GET /api/notifications/unread`, `PUT /api/notifications/read`) are returned only to the writer they are for, under the feed's rules: only comments, likes and follows that still exist, by live accounts the writer neither muted nor blocked nor was blocked by, about feed-eligible entries. They hold the actor's `id`, `username` and `avatarUrl`, the entry's id, date, number and title, and at most the first 140 characters of a comment the writer can already read; never entry text. The reader's id is the only query parameter. A single feed entry (`GET /api/entries/feed?entry=`) answers only a feed-eligible entry, with blocks applied, and is empty otherwise, so it cannot probe a private entry.
- The leaderboard counts only visible content. Achievements are returned only to their owner.

### Private share links

A writer can share one entry or one saved book version with someone who has no account (`modules/share-links`, [Features](./features.md#private-share-links)). The link is `https://<host>/s/<token>`; whoever holds it can read, without signing in, until it expires, its views run out, or the writer revokes it.

- **Token:** 32 bytes from `crypto.randomBytes` (256 bits), written as 43 base64url characters. Only its SHA-256 is stored (`share_links.token_hash`, unique, never selected by default, never in an API answer or the data download), like refresh tokens. The token is in the creation answer only; the web shows it once, to copy, and builds the address in the browser. A lookup hashes the presented token and finds the row by its hash, so neither the lookup nor its timing compares secrets; a token that is not 43 base64url characters is refused before any query.
- **Expiry and limits:** an expiry is required, from one hour to 366 days ahead (`400 SHARE_LINK_EXPIRY_INVALID`); the web offers 1, 7 or 30 days or the end of a day up to a year ahead. An optional view limit (1 to 1,000) counts each opening of the entry or download of the book in one conditional `UPDATE`, so concurrent readers cannot pass it. A writer has at most 100 unexpired links (`400 SHARE_LINK_LIMIT_REACHED`), counted under a transaction-scoped advisory lock. Revoking deletes the row. Expired rows are deleted as the writer next makes or lists links.
- **Making a link:** `/api/share-links` needs a session and acts only on the writer's own entry (outside the recycle bin) or book version (`404 ENTRY_NOT_FOUND` / `BOOK_VERSION_NOT_FOUND`); a sealed time capsule is refused (`409 ENTRY_SEALED`). The writer chooses whether the reader sees the mood (with its feelings) and the tags; both are off by default and always off for a book. The optional note (`label`) is never shown to the reader. Making links is throttled at 30 per 15 minutes.
- **What the reader gets:** `GET /api/shared/:token` (`@Public()`) answers an entry's date, time of day, title, text (Markdown or plain), its attachments' IDs, names, types and sizes, and the mood and tags only if chosen. Never the entry ID, diary, author, people, history, comments, storage keys or anything else of the account. A book version answers its title, author, format, file name and size. The web renders the text with the journal's Markdown renderer (react-markdown, no raw HTML), with mentions and `[[date]]` references as plain text and no link into the app.
- **Files:** `GET /api/shared/:token/attachments/:id` (and `…/poster`) serves only attachments whose row is on the shared entry and the writer's, by attachment ID, through the same response code as the owner's file route (stored type from the allowlist, `nosniff`, safe `Content-Disposition`, SVG and text as sandboxed downloads, single byte ranges). It never goes through the authenticated `GET /api/attachments/file/:key`. `GET /api/shared/:token/file` sends a book version's stored file as a download (`Content-Disposition: attachment` and `Content-Security-Policy: default-src 'none'; sandbox`, so an HTML book never runs on the app's origin) and counts a view. When a limited link's last view is used, that view's pictures still load for an hour, then stop.
- **One answer for every refusal:** a malformed, unknown, expired, used-up or revoked token, a link whose entry is in the recycle bin or sealed, whose book version or account is gone or deleted, and an attachment of another entry all answer the same `404 SHARE_LINK_NOT_FOUND`, so the answers never tell whether a token existed. Each request checks all of it in one query (live account, entry not binned or sealed, version still the writer's, expiry).
- **Binning or sealing an entry ends its links:** an `AFTER UPDATE OF deleted_at, sealed_until` trigger on `entries` deletes an entry's links the moment it goes to the recycle bin or is sealed, whatever code path does it, so restoring the entry does not bring a link back. Deleting the entry, the book version or the account deletes its links through the foreign keys.
- **Headers:** every `/api/shared/…` answer, errors included, carries `Cache-Control: no-store` (a revoked link stops at once, also for shared caches), `X-Robots-Tag: noindex, nofollow, noarchive`, `Referrer-Policy: no-referrer` and `Cross-Origin-Resource-Policy: same-origin` (no other site can embed the files). They are set by an Express middleware (`sharedResponseHeaders`, mounted by `configureApp` on `/api/shared` right after helmet, whose `Referrer-Policy` and `Cross-Origin-Resource-Policy` it replaces, and before CORS) as the request comes in, not by a Nest interceptor, which runs after the guards: so the throttler's `429`, a switched-off `publicSharing`'s `503 FEATURE_DISABLED`, a pipe's `400`, the `404` of an unknown path, an uncaught `500`, a CORS preflight and the streamed files and byte ranges all carry them (`configure-app.spec.ts` and the `sharing` contract spec check each). The web NGINX sends `no-referrer` and `X-Robots-Tag` for `/s/…` (and the pages emailed links open: `/reset-password`, `/complete-sign-up`, `/verify-email`) too and leaves `/s/…`, `/api/shared/…` and those pages out of its access log; the page also adds `robots` and `referrer` meta tags.
- **No session on the page:** `/s/<token>` is rendered by `main.tsx` before the app: no `AuthProvider`, no router, no refresh call, no request but `/api/shared/…` (fetched with `credentials: 'omit'` and no referrer), and no app navigation around it.
- **Logs and metrics:** the request log and HTTP metrics name the route `/api/shared/:token…`, never the token. Proxies in front of the web and API (Traefik, Cloudflare) may log full paths: keep their access logs off for these paths or treat them as secret.
- **Ingress:** only `/api/auth/sso` goes through the Keycloak OAuth2 Proxy (`sso-ingress.yaml`, and the canary IngressRoute); `/api/shared` falls under the open `/api` ingress and `/s/` under the web one, so a reader without an account reaches both.
- **Rate limits:** opening a link and downloading a book are throttled at 60 per 15 minutes per IP, its files (pictures, video ranges) at 600; with 256-bit tokens, guessing is not a practical attack either way.
- **Sharing switched off:** while the `publicSharing` [flag](./architecture.md#feature-flags) is off, every `/api/shared/…` request answers the same `503 FEATURE_DISABLED` whatever the token (so it tells nothing about one), no link is made, and a writer can still list and revoke theirs. Nothing is deleted: a link opens again, with its expiry and views, once the flag is on.

## Abuse Controls

Rate limits (`thoughty-server/src/common/rate-limit.constants.ts`):

| Policy | Limit | Applies to |
|---|---|---|
| Default | 100 per 15 min | every route except health and metrics (`GET /api/auth/me` included) |
| Auth attempts | 5 per 15 min | register and its completion, login, OAuth, 2FA verify and resend |
| Token refresh | 30 per 15 min | refresh, per account (`RefreshThrottlerGuard`, below); opt-in email unsubscribes, per address |
| Token refresh per address | 300 per 15 min | every refresh from one address, whatever the account |
| Password recovery | 3 per hour | forgot password, reset password, verify email |
| Account security | 5 per hour | password change, verification resend, 2FA changes, session revocation, account deletion |
| Social writes | 30 per 15 min | follows, comments, comment controls, likes, saves |
| Import writes | 300 per 15 min | app-import batches (`/api/io/import/entries`, `/api/io/import/attachments`) |
| Draft writes | 300 per 15 min | composer draft autosave and discard (`PUT`/`DELETE /api/composer-draft`); the web saves at most once every three seconds |
| Contact messages | 5 per hour | the Contact page form (`POST /api/contact`), per address |
| Share link writes | 30 per 15 min | making a private share link (`POST /api/share-links`) |
| Shared link reads | 60 per 15 min | opening a private share link and downloading its book (`GET /api/shared/:token`, `…/file`) |
| Shared link files | 600 per 15 min | a shared entry's files and video ranges (`GET /api/shared/:token/attachments/…`) |

- **Signed-in requests are counted per account, under a ceiling per address.** The global guard, `AccountThrottlerGuard` (`common/rate-limiting/account-throttler.guard.ts`, registered after the global JWT guard), applies each route's limit above per account when the request is signed in, so writers behind one address (an office, a school, a carrier's NAT) reloading the journal do not use up each other's budget. Every signed-in request from one address also counts against a ceiling of 3 times the route's limit (`ADDRESS_CEILING_FACTOR`; 300 per 15 minutes for the default), so many accounts at one address cannot multiply the limits; a request its own account's limit refused does not count against that ceiling, so one writer over their limit cannot lock out the others there. Signed-out requests, and every request to a public route (sign-in, sign-up, password recovery, the Contact form, private share links, the personal access token API, which the JWT guard lets through without reading a token), are counted per address at the route's limit, exactly as before. The account is only ever the one the JWT guard verified from the access token's signature (`request.user`), never a header or anything else the client sends; a request with no valid token to a protected route is refused `401` before it is counted. Each route keeps its own counters, keyed by route, then by account (`account:<id>`), by address for the ceiling (`accounts-at:<ip>`) or by address alone. A refused request answers `429 RATE_LIMITED` with `Retry-After` (seconds); the `X-RateLimit-*` headers of an accepted one describe the account's own budget. `GET /api/auth/me` now simply has the default limit, counted this way (100 per account, 300 per address).
- Counters use Redis when `REDIS_URL` or `REDIS_HOST` is set (`common/rate-limiting/redis-throttler.storage.ts`), so every API pod shares them. While Redis is unreachable (not connected yet at startup, reconnecting after a drop, or not answering within 500 ms) each request is counted in the pod's memory at once: the client is created with `disableOfflineQueue`, so a command is refused instead of waiting for the reconnect, and at most 1,000 commands wait on a stalled connection. The API connects at startup without waiting for Redis and keeps reconnecting in the background; once Redis answers again requests use it. One warning (`Redis is unreachable …`) is logged when the outage starts and one line (`Redis answers again …`) when it ends, not one per request.
- The fallback keeps the API usable and still limits each client, but during the outage limits are per pod (with N replicas a client gets up to N times each limit, as the Service spreads its requests), and the hits counted in memory are not carried to Redis afterwards. A Redis outage therefore needs attention rather than being ignored; its warning is the signal.
- **Refresh is counted per account too.** `POST /api/auth/refresh` is a public route authenticated by its cookie, so a per-address limit alone would let writers behind one address (an office, a school, a carrier's NAT), or one writer reloading many tabs, use up each other's refreshes. `RefreshThrottlerGuard` (`auth/guards/refresh-throttler.guard.ts`) keys the 30-per-15-minutes count on the account the cookie's token was signed for (`AuthSessionService.refreshTokenAccount`: the `REFRESH_SECRET` signature and expiry, no query), so a forged or expired token counts against its address, as does a request with no cookie, exactly as before. The global throttler still caps all refreshes from one address at 300 per 15 minutes. A token stolen from a writer could use up that writer's refreshes for the window; it already lets its holder do far more. Sign-in, two-factor, sign-up and password routes keep their per-address limits unchanged. A refused refresh answers `429 RATE_LIMITED` with `Retry-After` (seconds) and leaves the cookie alone.
- Address counters (signed-out requests, public routes and the per-address ceiling) key on the client IP (`req.ip`), so Express must trust exactly the proxies in front of the API (`TRUST_PROXY`, `common/security/trust-proxy.ts`). swirl-cloud sets `2` (Cloudflare or the HA tunnel, then Traefik, which rewrites `X-Forwarded-For` from anyone else). Unset, production trusts private-network proxies and other environments trust none. If a proxy is added or removed in front of the API, change `TRUST_PROXY`: too few hops makes every client share one counter, too many lets clients choose their own IP.
- Register and login reject requests that fill the hidden `website` bot-trap field.
- Body limits (`common/security/request-payload-limits.ts`): JSON `1mb` and forms `256kb`, set with `REQUEST_BODY_LIMIT`, `REQUEST_JSON_BODY_LIMIT`, and `REQUEST_FORM_BODY_LIMIT`. Only `/api/io/preview` and `/api/io/import/*` accept JSON up to `8mb` (`REQUEST_IMPORT_BODY_LIMIT`), so a 5 MB text import fits once escaped. The ingress caps bodies at 10 MiB, except `POST /api/attachments/upload`, which takes 51 MiB (a 50 MB video and its multipart framing).
- Uploads take one file and one scalar field, with no nested field names (`common/multipart-limits.ts`): at most 50 MB on the attachment upload route (5 MB unless it is a video, checked once it has arrived), 1 MB for a poster frame (no field), 5 MB elsewhere. App-import file batches take up to 8 files of 5 MB; imported videos use the upload route.
- Search is capped at 500 characters and uses bound parameters only.
- Client input the database rejects answers `400` (`DatabaseInputExceptionFilter`).

## Secrets

Production secrets live in Vault and reach the cluster through External Secrets (`infra/k8s/overlays/swirl-cloud/external-secrets.yaml`). The standalone profile uses [Vault Agent](./standalone-vault.md). Nothing secret is committed. Setup and rotation: [Deployment](./deployment.md#configuration-and-secrets).

- `JWT_SECRET`, `REFRESH_SECRET`, `TWO_FACTOR_SECRET`, `UNSUBSCRIBE_SECRET` (signs email unsubscribe links; derived from `JWT_SECRET` if unset; one value across API and worker, and rotating it voids the links in emails already sent)
- `CONFIG_ENCRYPTION_SECRET`: the most sensitive value. Leaking it exposes stored provider tokens and AI keys; losing it makes them unreadable.
- PostgreSQL and backup credentials, S3 keys, the optional shared `OPENROUTER_API_KEY`, cloud-provider OAuth client secrets, and SMTP credentials

In production the API and worker refuse to start without `CONFIG_ENCRYPTION_SECRET`, or when `JWT_SECRET` or `REFRESH_SECRET` (and `TWO_FACTOR_SECRET` or `UNSUBSCRIBE_SECRET`, when set) is missing, an example value, or shorter than 32 characters (`auth/auth-secrets.ts`). Development keeps working defaults.

## Data Protection

- **Encryption at rest:** personal OpenRouter keys and cloud-provider tokens are encrypted with AES-256-GCM using `CONFIG_ENCRYPTION_SECRET`. Other settings are plain text. Personal keys are checked with OpenRouter before storage and shown only as their last five characters.
- **Cloud provider failures:** a refused or failed provider request is logged with the provider, the step and the HTTP status only (`cloud-sync/providers/provider-failure.ts`), and an unreachable provider with the host only (`cloud-operation.ts`). Provider response bodies, which can echo the authorization code, tokens or file details, are never logged or passed on (they are discarded unread, apart from the Dropbox folder check that looks for a conflict), and the error the API returns carries only its code and a fixed message naming the provider.
- **Settings API:** `GET /api/config` returns only user preferences, and `POST /api/config` accepts only an allowlist of preference keys with validated values (`config/dto/config.dto.ts`); credentials, cloud tokens, and sync state cannot be read or written through it.
- **Attachments:** a MIME allowlist (images including SVG, PDF, text, audio, MP4, WebM and QuickTime video) and the size limit of the type (5 MB, 50 MB for a video) are checked before storage. A video is recognized by its first bytes (an MP4-family or QuickTime `ftyp` brand or a legacy QuickTime atom, or an EBML header whose document type is `webm`; HEIF pictures, M4A audio and other Matroska files share those containers and are refused) and stored with the type they show; a file that claims to be a video without being one is refused with `400 ATTACHMENT_CONTENT_MISMATCH` before anything is stored. The upload route writes the file to a temporary file as it arrives, so multer's 50 MB limit stops an oversized body there (`413`) instead of in memory; the file is streamed to storage and the temporary file deleted once the request is answered, whatever the outcome (`TempUploadCleanupInterceptor`). A video's poster frame (`POST /api/attachments/{id}/poster`) must be the caller's own video, not in a sealed capsule, and a JPEG of at most 1 MB and 4096 pixels a side by its signature and frame header; it gets its own random key on the video's row. Objects use random UUID keys in private buckets. The file route serves a file, or a video's poster frame, only to the owner of its attachment (anyone else gets `404`), with the stored type from the allowlist, `X-Content-Type-Options: nosniff`, and a safe `Content-Disposition`. It answers a single `Range: bytes=` range with `206` and `Content-Range` (a range past the end with `416 ATTACHMENT_RANGE_NOT_SATISFIABLE`, several ranges or a malformed one with the whole file) and sends `Accept-Ranges: bytes`. Only raster images, audio, video, and PDF are shown inline; SVG and text are downloads with a sandboxing CSP. The web app loads every file with the session into a `blob:` URL, which `media-src 'self' blob: data:` allows for the video player; a video is fetched only when the reader presses play.
- **Book sources:** a book reads only the writer's own entries. A saved search must be theirs (`404` otherwise), and deleting one deletes only the writer's own versions of it (by `user_id` and `scope_key`) and its stored filters are applied with bound parameters, as in the journal. Hand-picked entry IDs are parsed as integers, capped at 500, and every one must belong to the writer and be outside the recycle bin, or the request is refused with `BOOK_PICKED_ENTRIES_UNAVAILABLE`; `GET /api/books/picked-entries` describes only the writer's own entries and lists the rest as missing without saying why. A book about a person adds no route: it is a saved-search book, and a saved search can only name the writer's own person.
- **Time capsules:** a sealed entry's row holds no title, text, tags, mood or feelings (they wait in `time_capsules` until it opens), so no read path that looks at entries can show them; its responses carry only an empty text and `sealed_until`, attachment files and transcription answer as missing or `409 ENTRY_SEALED`, edits, task ticks, visibility changes and per-entry AI requests are refused with `409 ENTRY_SEALED`, bulk visibility and tag changes skip it, it has no revisions (sealing happens only when an entry is created), and a check (`chk_entries_sealed_private`) keeps it private. A spec reads every documented `GET /api/entries…` route (the open tasks, the reader and the comfort reads included, which also leave sealed entries out by query; and people, mood stats, the words used most, books and the recycle bin) for a sealed entry's words and fails when a new route is not checked. Opening early (`POST /api/entries/:id/unseal`) acts only on the writer's own entry. The opening email goes once, only to the verified address of a live account, carries the title and at most 200 characters of plain text, all HTML-escaped, and the worker logs only the user ID. Exports and the data download are the writer's own copy, so they keep the sealed text, marked sealed.
- **PIN lock:** diaries and single entries can be locked behind one 4-digit PIN per account. It is an **access gate, not encryption**: the text stays in PostgreSQL as it was, and the UI says so ("Hides these entries behind your PIN on this account. It is not encryption."). A 4-digit PIN is a weak secret, so the lockout is what protects it: the PIN is a bcrypt hash (cost 12, like passwords, `content_pins`), checked one try at a time per writer under a row lock, and wrong tries are counted in the database, so neither a restart nor parallel requests reset or skip them: four wrong PINs in a row are only wrong (`403 CONTENT_PIN_INCORRECT`), the fifth blocks tries for a minute and each further one doubles the wait up to a day (`429 CONTENT_PIN_BLOCKED`, also for the right PIN while blocked); a right PIN clears the count. The PIN routes are throttled too (`contentPin`, 20 per 15 minutes per route). Changing or removing the PIN needs the current PIN (a wrong one counts as a try) or, for a forgotten PIN, the account password and, when two-factor authentication is on, the emailed code (an account without a password confirms with the emailed code alone, `content-pin` challenges of `TwoFactorService`); a change or removal ends every unlock, and removing the PIN removes every lock. An unlock (`POST /api/content-lock/unlock`) is a random 32-byte token shown once, of which only the SHA-256 is kept (`content_unlocks`); the web keeps it in the tab's memory only and sends it as `X-Content-Unlock`. `ContentUnlockMiddleware` reads it before any guard, on the primary, and extends it by 15 minutes; it ends after 15 minutes without a request, when the writer blurs again (`DELETE /api/content-lock/unlock`), signs out, reloads or closes the tab, and the web also ends it after 15 minutes without a key, click, touch or wheel. It unlocks only its own writer's content: another writer's token, a malformed or ended one, or a database error unlocks nothing. Until unlocked, the server never sends a locked entry's text, tags, mood, feelings, attachments, revisions or files: the entry and calendar lists and the recycle bin show a placeholder (date, title, diary, flags, `withheld: true`); entry-specific routes (history, backlinks, task ticks, edits, attachment files and posters, transcription, AI summary, chat and its history, lifting a lock, deleting a locked diary, the data download) answer `423 CONTENT_LOCKED`; everything that reads text or aggregates it leaves locked entries out (search and every filter that reads content, random, reader, comfort reads, open tasks, Highlights and On this day, tags, stats and their AI readings, the year in review and its mood, books, book previews and picked entries, every export, AI duplicates, meaning search, retagging and inspiration, people counts and person dates, memoir word counts). The data download keeps everything (it is the writer's data) but needs the unlock while anything is locked. Work done without a request (On this day, monthly recap, memoir and time capsule emails, cloud sync even when started by an unlocked request, every worker job) leaves locked content out: the request context (`AsyncLocalStorage`) holds no unlock there. Locked content is always private: locking makes the diary or entry private, a trigger keeps any locked entry private (`entries_copy_diary_lock`, also for entries moved into a locked diary), making one public is refused (`409 CONTENT_LOCKED_PRIVATE`), a share link to a locked entry, or to a book version holding one, does not open while it is locked (the link is kept and opens again once the lock is lifted), and new links to them are refused. A saved book version that holds an entry locked now downloads only with the unlock. The entry list cache keys on the unlock. The real-API contract suite `content-lock` calls each gated route locked and unlocked and checks no locked answer carries the locked words. PINs and tokens are never logged.
- **Writing times:** the `timeZone` that `GET /api/stats` takes reaches SQL only as a bound parameter of `AT TIME ZONE`, after `@WritersTimeZone()` has checked it is a named zone `isValidTimeZone` knows (up to 64 characters, starting with a letter), so neither text nor an offset PostgreSQL would read the other way round gets through; the counts and the personal records read only the writer's own entries, and a record answers only the entry's ID, date and number, which the entry's own permalink then checks like any other.
- **Words used most:** `GET /api/stats` reads the texts of the writer's own entries of one month only (`user_id`, the diary and the dates bound as parameters, `today` checked by `@WritersDay()`), never the recycle bin or a sealed time capsule (`sealed_until IS NULL`), and counts their words in the API; the list goes only to the writer, and the web gives each word the `privacy-text` class so the privacy blur hides it.
- **Offline app shell:** the web's service worker (`/sw.js`, built from `src/serviceWorker/` by `scripts/serviceWorkerPlugin.ts`, registered by production builds only) keeps the build's public files (`index.html`, scripts, styles, fonts, icons, the manifest; PDF.js left out) in one cache per build (`thoughty-shell-<version>`, the version a hash of those files, older builds' caches deleted when a new worker activates). It never answers or stores anything under `/api/`, another method than `GET` (but the share target's post, below), or another origin, so no entry, token, shared file or API answer is ever in its cache. A page load goes to the network first and falls back to the cached `index.html` only when the network fails; that copy is stored under `/index.html` alone, never under the address asked for, so a share link token or shared text in an address never becomes a cache key. On install it checks that the `index.html` it fetched loads only files of its own build (during a rollout it could come from a pod on the other one) and otherwise fails, to be tried again. It installs and takes over at once (`skipWaiting`, `clients.claim`); since a page load is network first, an online visit always runs the deployed build. The web NGINX serves `/sw.js` and `/index.html` with `Cache-Control: no-cache` and the security headers, and the page registers the worker with `updateViaCache: 'none'`; the CSP's `default-src 'self'` covers the worker script and its same-origin requests. A cached page keeps the headers it was served with (CSP included).
- **Journal opened offline:** so the journal opens when Thoughty cannot be reached, the web remembers the writer of the last session confirmed on this browser (`localStorage` `thoughty.offlineUser`: id, email, username, sign-in provider, email-verified and two-factor flags; no token, avatar or profile text) and the settings that change how the app looks and reads (`thoughty.offlineDisplay`: language, theme, high contrast, font, size, colour, spacing, quiet mode; nothing else of the settings). Both go with every session that ends (`endSession`), and a refresh refused on load removes them. A load whose refresh reaches no working API (a network error or a `5xx`), or gets any answer but a refusal (`401`, `403`) or a token, opens the journal for that writer with no token (`offline` in `AuthContext`); every request then first tries the refresh again, as does the browser's `online` event, and the refresh cookie decides: a new token (and `/me`, which says whose session it is) ends offline mode, a refusal ends the session there. A session that ends while it is being got back (signed out in this tab or another one while `/me` is read) is not brought back, and a tab still loading that hears another tab sign out uses neither the token its refresh got nor the remembered writer, so a sign-out is never undone by a restore that was already under way. Offline mode shows only what the device already holds: the composer draft kept in `thoughty.composerDraft.<userId>` (see Composer drafts) and nothing the API would have to answer. A refresh that reaches no working API never ends a session (losing the connection signs no one out); only the server's refusal does. **A refresh the API asks to wait for** (`429`) says nothing about the session either: the web keeps the wait (`Retry-After`, an HTTP date or seconds; without one 5 seconds, doubling with each refusal in a row; never over 15 minutes, the API's window, nor under a second, plus up to a quarter of it, at most 30 seconds, so browsers sharing an address do not all retry at once) in `localStorage` `thoughty.refreshRetryAt` (`contexts/refreshThrottle.ts`). Every tab reads it under the cross-tab refresh lock before sending a refresh, so no tab, request, `online` event or reload sends one until the wait is over. On load, a `429` opens the journal offline for the remembered writer at once rather than holding the page for a wait of up to minutes; with no writer remembered there is no journal to open, so the sign-in page shows, as for any visitor. A `429` to the refresh a request asked for when its token expired keeps the writer signed in the same way, offline, without sending the expired token again. Either way, once the wait is over the session is tried again on its own; any answer ends the wait. **A `/me` that cannot say whose the session is** ends nothing either: once the refresh has given a token, only a `401` or `403` from `GET /api/auth/me` ends the session. A `429` (its wait kept like the refresh's, in `thoughty.meRetryAt`, so no tab or reload reads `/me` until it is over), a `5xx`, an answer that cannot be read or none keep the token and open the journal offline for the writer remembered here, if the token is theirs (its `userId` claim, read without checking the signature, which the API does on every request; a writer shown offline whose token turns out to be another account's ends there). `/me` is then read again on its own, after the wait asked for or after 5 seconds doubling with each failure in a row up to 15 minutes, and when the connection returns, with the token held (refreshed once first if `/me` refuses it, since it may have expired meanwhile); the answer ends offline mode or the session. With no writer remembered here for that token, there is no journal to open, but the writer is signed in: rather than the sign-in page, which would ask them for a password they need not give and spend sign-in attempts, the page says **Thoughty can’t be reached right now** (`unreachable` in `AuthContext`, `SessionUnreachablePage`), with **Try again** and **Logout**, and opens the journal as soon as `/me` answers; a sign-out in another tab, or another writer signing in there, ends it. A sign-out the server never heard (offline, or the API down) is kept (`thoughty.signOutPending`) and sent first on the next load, which then stays signed out, so the refresh cookie cannot sign the writer back in; a new sign-in clears it.
- **Composer drafts:** a draft is private text, handled like an entry: stored in plain text in PostgreSQL as entries are (no application-level encryption), never logged (request logs carry the method, path, status and user ID only), read and written only by its owner through `/api/composer-draft` (keyed by the signed-in user, so there is no ID to guess), within the entry limits (`SaveComposerDraftDto`, and table checks behind it), and written with bound parameters. A save or discard names the revision it was made on, and one made on any other is refused with `409 COMPOSER_DRAFT_CONFLICT`, so a stale device never silently overwrites newer text. The web keeps a copy in `localStorage` (`thoughty.composerDraft.<userId>`) for reloads and lost connections, removed on publish, discard and sign-out; its text in the offer to continue takes the privacy blur. The draft is part of the data download and goes with the account.
- **Reread reminders:** `PUT`/`DELETE /api/entries/:id/reread-reminder` act only on the writer's own entry outside the recycle bin (`404 ENTRY_NOT_FOUND` otherwise) and refuse a sealed time capsule (`409 ENTRY_SEALED`, with `chk_entries_reread_open` behind it). The body takes only `rereadOn` and `today`, both strict `YYYY-MM-DD` days; `today` must be the UTC day or the one before or after it (every time zone is within a day of UTC, `@WritersDay()`, which every other route that takes the writer's day checks the same way), and `rereadOn` from the day after it up to 50 years ahead (`400 REREAD_DATE_INVALID`). The day is written through the entity, never into SQL text, and `reread_on` is sent only in the owner's own entry responses, never in the public feed or a share link.
- **Recycle bin:** deleted entries are hidden from every other feature (the journal calendar included) and lose their private share links at once; they stay 30 days, then are purged with their revisions, attachments (with video poster frames), chat, comments, and likes. Deleting forever purges at once. Storage failures are logged by key and do not stop the purge.
- **Deleted accounts:** an hourly worker job permanently deletes accounts deleted more than `ACCOUNT_PURGE_AFTER_DAYS` ago: first their files in object storage, then the user row, whose foreign keys cascade to everything they own or wrote, including their comments, likes, follows, and feature requests. If any file cannot be deleted, the account is kept and retried on the next run.
- **Life eras:** every `/api/life-eras` route reads and writes only the writer's own eras (`404 LIFE_ERA_NOT_FOUND` otherwise). The journal's `eraId` filter matches an era only when it belongs to the entry's owner, with the ID bound as a parameter, so another writer's era ID finds nothing; a saved search or memoir answer that names an era must name one of the writer's own.
- **Imported calendars:** every `/api/calendar` route reads and writes only the writer's own events (`user_id` bound as a parameter). The `.ics` file (`POST /api/calendar/import`, one file of at most 5 MB kept in memory, `413 PAYLOAD_TOO_LARGE` past it) is read as text by `parseIcs`, never run or stored: only each event's UID (hashed when longer than 255 characters), title and place (cut to 200 characters, shown as text and blurred by privacy blur) and its times are kept (for a repeating event, its rule's known parts and at most 1,000 extra and 1,000 removed occurrences, as JSONB), at most 10,000 per writer under a per-writer advisory lock. A rule's occurrences are worked out in memory for the one day asked, from the period holding that day (a rule with a `COUNT` from its first day, at most 100,000 periods), so a rule cannot make a day's list grow without bound. The `date` and `timeZone` of `GET /api/calendar/events` reach SQL only as bound parameters, after `@IsISO8601` and `@WritersTimeZone()`; so do the days of `GET /api/calendar/days` (at most 200, each `YYYY-MM-DD` and a real date, bound as one `date[]` array), whose repeating events are worked out per day as above, so one request does at most 200 days' work. The events are in the data download and go with the account.
- **People:** people are the writer's private notes, never platform users or accounts. Every `/api/people` route reads and writes only the writer's own people (`404 PERSON_NOT_FOUND` otherwise), and a merge needs both people to be theirs. Links only ever join a writer's entries to their own people, so the journal's `personId` filter (a bound parameter) finds nothing for another writer's person, and a saved search can only name the writer's own. The feed and share texts carry no person data, and the web renders mentions as links only in the writer's own journal. Before an entry is shared (made public, given a private share link or exported as an image card) the web lists the people it names, from the writer's own People list already loaded in the journal (`src/utils/peopleCheck.ts`); the check sends nothing and stores nothing, and **Replace** saves the new words through the ordinary `PUT /api/entries/:id`, so the earlier text stays as a revision only the writer sees. A person's birthday or anniversary is set only through `PATCH /api/people/:id` on the writer's own person (whitelisted `date` fields, month and day checked in the service and again by database checks), and Highlights reads only the writer's people and counts only their own entries outside the recycle bin and sealed time capsules, so a capsule's mention is never revealed by the count. A reach-out reminder and the last contact are set the same way (`reachOutDays` only from the offered intervals, `lastContactOn` a real day not after today) or by `POST /api/people/:id/contacted` with the writer's own day, and the reminders in Highlights read only the writer's people and the dates of their own entries outside the recycle bin and sealed time capsules. Notes on a person are set only through the same `PATCH` on the writer's own person (a string of at most 2,000 characters), shown only on the writer's People page as text (React escapes it, never as HTML or Markdown) under the privacy blur, and never reach Highlights, the feed, share texts, books or AI requests. Groups are set the same way (an array of at most 10 strings of 1 to 40 characters, saved as a bound `text[]` parameter), read back only by the writer, shown as text, and the spelling lookup reads only the writer's own people. Mentions over time read only the writer's own person (`404 PERSON_NOT_FOUND` otherwise) or the writer's own people in the group (a string of 1 to 40 characters, compared in the service, the people's ids sent as a bound `int[]`), and count only their own entries outside the recycle bin, sealed time capsules and, unless unlocked, locked entries, so the counts and moods reveal nothing a lock or a capsule hides.
- **Data download:** includes recycle-bin entries, revisions, attachment metadata, settings, social and memoir data (photo stories included), stored mood readings, saved searches, life eras, imported calendar events, people (with their birthday and anniversaries), diary writing goals and default templates, the "On this day", monthly recap, year in review and writing reminder email settings (with each diary's own reminder hour), time capsules (sealed entries with their text, marked `sealedUntil`, and each capsule's opening schedule and `openedAt`), the composer draft still being written, private share links (what each shares, its note, options, expiry and views, never its token or hash), the past year's account activity with the new-browser email setting (`accountActivity`), and the personal access tokens (`accessTokens`: name, hint, scopes, time zone and dates, never the token or its hash). It leaves out the password hash, session tokens, the personal AI key, cloud tokens and sync internals, and AI chat history.
- **App imports:** Day One and Journey exports, daily-notes ZIPs and Google Keep's Takeout are parsed in the browser ([ADR 0020](./adr/0020-browser-side-app-imports-and-streamed-archives.md)); the API never receives or unpacks a ZIP. Journey HTML goes through an inert `DOMParser` that keeps only text, basic formatting, and `http`, `https`, or `mailto` links. Imported entries are private and go only to the writer's own diaries. A batch holds at most 200 entries and is saved in one transaction. Every file is checked before any is stored.
- **ZIP reading** (`thoughty-web/src/utils/zipReader.ts`): a compressed file is unpacked through a counter and fails as soon as it grows past the uncompressed size its directory entry gives, so a crafted archive can never unpack more than the sizes checked before reading it (zip bomb); the reader reports Unix symbolic links and names that are not UTF-8. The daily-notes and Google Keep imports (`readDailyNotes.ts`, `readKeep.ts`, sharing the caps in `appImportArchive.ts`) are stricter than the app exports: it refuses an archive of more than 50,000 files or a directory over 32 MB before reading the directory, and notes that declare more than 200 MB in all; it leaves out (and counts) notes over 5 MB, symbolic links, names that are not UTF-8, and any path that is absolute, uses `..`, a backslash, a drive letter, a control character or a character Windows refuses (`safeZipPath`, the zip-slip guard), and never uses such files as attachments; an embedded file's relative path is resolved inside the archive and one that climbs above its top is not found; a Keep note's file is looked up by its bare name in the note's own folder only. Nothing is written to disk. For every app import, a file to attach whose declared size is over the attachment limit (64 MB for a photo to scale down) is refused before it is unpacked. Source IDs are checked by the API (`[A-Za-z0-9._:/-]`, 100 characters); a note whose path (or, for Keep, file name) has other characters is sent as its day and a 64-bit FNV-1a hash of it.
- **Markdown export:** streams one attachment at a time, re-checks the limit of its type (5 MB, 50 MB for a video), keeps videos to 2 GB per archive, and builds paths from sanitized names.
- **Inline images:** an entry names a picture by its attachment ID (`attachment:<id>`), never by its storage key. On every save (`POST /api/entries`, `PUT /api/entries/:id`) a reference stays only when its attachment is the writer's and on this entry, or on no entry yet (it then joins this one), or was already in the saved text; any other becomes its alt text (`EntryInlineImagesService`), so a reference can never reach another writer's or another entry's file, and renderers resolve references against the entry's own attachments only. File imports turn every reference into its alt text; app imports keep only references to the files the browser sends next for that entry, resolved when they are stored. The public feed sends the alt text in place of each reference. Books and documents embed only the entry's own pictures, read through the same checks as entry images (passive image signature, bounded dimensions, 5 MB each, 25 MB in all).
- **Memoir:** answers are private entries. Skip and **Not this week** act only on the signed-in writer's own program (`404 MEMOIR_NOT_STARTED` otherwise) and take no input. A photo story (`POST /api/memoir/photo-answers`) takes only the writer's own upload (`404 ATTACHMENT_NOT_FOUND` otherwise) that is on no entry yet (`409 MEMOIR_PHOTO_IN_USE`) and is a JPEG, PNG, GIF or WebP picture (`400 MEMOIR_PHOTO_NOT_IMAGE`, so no SVG), and is always a private entry; its caption is escaped as Markdown alt text, like any inline image's. Weekly emails go only to verified addresses of live accounts and contain the question and a link, never journal text.
- **"On this day" email:** off until the writer turns it on, and sent only to the verified address of a live account. It is the one email that carries journal text, so it carries as little as is useful: per entry the title and at most the first 200 characters as plain text, and a link to the entry that still needs a session to open. Private entries are included on purpose, because the address is the owner's own and verified; entries in the recycle bin never are. Titles and excerpts are HTML-escaped. The unsubscribe link (and the RFC 8058 `List-Unsubscribe` one-click header) carries `<userId>.<HMAC-SHA-256 of a fixed purpose and the user ID, keyed by UNSUBSCRIBE_SECRET>`, checked in constant time by the public `POST /api/on-this-day-email/unsubscribe?token=…` (token-refresh throttle): it can only turn that writer's email off, reveals nothing, answers the same success whether or not anything changed, and answers `400 ON_THIS_DAY_UNSUBSCRIBE_INVALID` to anything not signed with the key. The settings routes read and write only the writer's own row, and a chosen diary must be the writer's (`404 DIARY_NOT_FOUND`). Worker logs carry the user ID and, on failure, the error name and SMTP reply code only, never the address, the SMTP message, or entry text.
- **Monthly recap email:** the same rules as the "On this day" email (off until turned on, verified address of a live account, the writer's own rows and diaries only, recycle bin left out, ID-only worker logs). It carries counts, the names of the top three tags and the average recorded mood, and one memory with its title and at most 200 characters of plain text, all HTML-escaped; no AI reads anything. Its unsubscribe token names the email: `recap.<userId>.<HMAC-SHA-256 of a purpose of its own and the user ID>`, so it can never turn the "On this day" email off, nor an "On this day" token the recap. The shared public `POST /api/email-unsubscribe?token=…` (token-refresh throttle, also the recap's one-click header) verifies either kind in constant time, turns off only that email for that writer, answers the same success (with the email's kind) whether or not anything changed, and `400 EMAIL_UNSUBSCRIBE_INVALID` otherwise. "On this day" tokens keep their original form, so the links already sent keep working at both routes.
- **Writing reminder email:** the same rules again (off until turned on, verified address of a live account, the writer's own row and diaries only, ID-only worker logs). It carries no journal content at all, only whether the day has been written (it is not sent when it has) and, outside quiet mode, the streak count. Its unsubscribe token is `remind.<userId>.<HMAC-SHA-256 of a purpose of its own and the user ID>`, verified by the shared `POST /api/email-unsubscribe` (also its one-click header), so it turns off only the writing reminders: the Profile one and every diary's own hour, whose emails carry the same token. A diary's hour can be set only on the writer's own diary (`404 DIARY_NOT_FOUND` otherwise), and the list answers only the writer's rows.
- **Year in review email:** the same rules again (off until turned on, verified address of a live account, the writer's own row and diaries only, recycle bin and locked entries left out, ID-only worker logs). It carries no entry text or title, only counts (entries, words, writing days, longest streak, busiest month), the names of the top five tags and the average recorded mood, all HTML-escaped, and in quiet mode only the tag names and the mood in words; no AI reads anything. Its unsubscribe token is `year.<userId>.<HMAC-SHA-256 of a purpose of its own and the user ID>`, verified by the shared `POST /api/email-unsubscribe` (also its one-click header), so it turns off only this email.
- **Live dictation:** the composer, the entry editor and focus mode use the browser's own speech recognition (Web Speech API), never Thoughty's server or an AI provider. Browsers may do the recognition on their maker's servers: Chrome sends the audio to Google's speech service, and other browsers may do the same or work on the device. So it is opt-in per use: it starts only on a press of the microphone button, stops on a second press, `Esc` or the end of the session, never starts or restarts by itself, and the first use shows a note saying where the audio may go before anything is recorded (remembered in that browser's `localStorage`, `thoughty.dictationNoticeSeen`). Only the words the browser returns are written into the draft; no audio is stored. The web app's `Permissions-Policy` allows the microphone for its own origin only (`microphone=(self)`), for dictation and the memoir recorder.
- **Share to Thoughty:** what another app shares to the installed app is posted (`multipart/form-data`) to `/share-target`, and the service worker receives it in the browser (`src/serviceWorker/shareTargetReceiver.ts`), so nothing is posted to the server: it answers with a `303` to `/share-target?title=&text=&url=` (each field cut to 50,000 characters), and keeps the shared files in its memory only, never in its cache or any storage, under a random id (`crypto.randomUUID()`) that address carries. The page asks for them as it loads (a `MessageChannel` message to the worker controlling it, `sharedFilesClient.ts`); the worker hands them over and forgets them, or drops them after two minutes if no page asked, and stays up only that long (`waitUntil`). The page holds them in memory until the composer takes them, checks each against the attachment types and sizes (`attachmentRejectionReason`), and they are uploaded with the entry through the usual attachment API, which checks them again. A post that reaches the web NGINX (no worker in that browser) is redirected (`303`, relative) to `/share-target?unreceived=1` with its body dropped unread (`client_max_body_size 100m` on that one location). The web NGINX sends that page with `Referrer-Policy: no-referrer` and `X-Robots-Tag` and leaves it out of its access log (`$thoughty_secret_link`), the page moves the text into the tab's session storage and replaces the address with `/journal` before the app renders, and the composer takes it out of storage once (`utils/shareTarget.ts`). The text goes only into the writer's own composer, as a private entry, and is rendered as text. Proxies in front of the web (Traefik, Cloudflare) may log full paths: keep their access logs off for `/share-target` as for the secret links.
- **Year in review:** computed on request and never public. Sharing posts only the text the writer edited, without tags unless chosen.

## AI Privacy

AI is optional and uses OpenRouter. A user's personal key, when set, replaces the shared key for all of their requests. While the `ai` [flag](./architecture.md#feature-flags) is off nothing is sent to OpenRouter: the AI routes answer `503 FEATURE_DISABLED`, auto-tagging on save is skipped, and a book's AI options are refused; a stored personal key can still be read (its hint) and removed.

| Feature | What is sent |
|---|---|
| Rephrase | the draft, up to 10,000 characters |
| Auto Tag | the draft, up to 10,000 characters, and its current tags |
| Entry chat | the entry, up to 10,000 characters, and up to 50 messages. Chats are stored per entry. |
| Discuss these entries | on request: the newest 50 entries the journal filters (and an optional date range) match, with date and title, up to 1,500 characters each and about 40,000 in all, and up to 50 messages; never a sealed capsule, nor a locked entry unless unlocked. Nothing is stored. |
| Entry summary | one owned entry, plus the writer's include and exclude notes |
| Get Inspired | tag names and counts from the 200 newest entries. No entry text. |
| Stats mood, tone, subjects | each time stats load with a key available: the 40 newest entries, with date, tags, and up to 1,200 characters each |
| Writing tendencies | aggregate word, subject, and writing metrics. No entry text. |
| Duplicate review | the 40 newest entries, up to 400 characters each |
| Meaning search | the query and the 100 newest entries, up to 1,200 characters each |
| Organize tags | the 300 newest entries, up to 400 characters each |
| Year mood arc | on request: up to 5 entries per month, 600 characters each. The reading is stored. |
| Weekly reflection | on request: up to 21 entries of the past seven days, spread across them, 1,000 characters each, never a locked entry (even while unlocked) or an archived one. The reflection is stored. |
| Book weaving | on by default in book export (strict or creative): the date and full text of each chapter's entries, in parts of about 20,000 characters. No images. |
| Book chapter framing | when chosen: each chapter's dates and text, cut to 20,000 characters, for the introduction and summary |
| Audio transcription | the one selected audio attachment, up to 5 MB |
| Memoir interview mode | on request (never when the memoir diary has AI off): the memoir question and the answer being written (whole up to 12,000 characters, else its first 4,000 and last 8,000), and the follow-ups already offered for it, at most 12. Nothing is stored. |

- **AI privacy mode per diary:** a diary's AI can be **On** (the default) or **Off** (`diaries.ai_mode`, set in Manage Diaries). With it off, nothing the server reads for a prompt includes that diary's entries, and every entry each AI table row above names is left out: the queries that feed a prompt add `aiReadableEntrySql()`/`AI_READABLE_WHERE` (`common/diary-ai`) on `entries.diary_ai_off`, which a trigger keeps equal to the diary's mode (as `diary_locked` is for the lock), so Stats readings, writing tendencies, Discuss these entries, meaning search, duplicates, tag organizing (plan and apply), Get Inspired, the weekly reflection and the year mood arc never read them, an entry saved in it is not auto-tagged, and the AI actions on one entry (summary, entry chat, transcription of its recording) answer `403 DIARY_AI_OFF`, as do memoir follow-ups when the memoir diary has AI off; a book holding one of its entries refuses AI weaving and framing (`400 BOOK_AI_DIARY_OFF`) and builds as a plain book. **Rephrase** and **Auto Tag** send text the app holds (a draft, or an entry's text for rephrasing one or several entries): the web app offers neither in the composer of such a diary nor on its entries, and bulk Rephrase skips them, and each request also names the diary of its text (`diaryId` on `POST /api/ai/fix-writing` and `/api/ai/suggest-tags`: the composer's diary, or the default one while all diaries are shown, or the entry's), which the server checks before anything reaches the provider (`AiDiaryGateService`): `403 DIARY_AI_OFF` for a diary with AI off, `404 DIARY_NOT_FOUND` for one that is not the writer's. A request naming no diary is still served, so older clients keep working; the diary it names is the client's word, so for these two the web app stays the first gate. The memoir form offers no transcription of a new recording or follow-ups there; a recording no entry holds yet names the memoir diary when it is transcribed (optional `diaryId` body on `POST /api/attachments/{id}/transcribe`), which the same gate checks after the entry's own diary, if any (a request naming none is still served, and a transcript already kept is returned without a provider call). The journal-wide AI actions read what the server allows, so the web app only explains: while the diary shown has AI off it offers no Discuss these entries, duplicate scan or meaning search, and the weekly reflection, the Stats readings and writing tendencies and the year mood arc say the diary has AI off in place of their AI reading (no request is offered); with all diaries shown they say diaries with AI off (or asking each time) were left out. When the server refuses Rephrase or Auto Tag for AI off, the web app shows the translated refusal (`apiError_DIARY_AI_OFF`) and loads the diaries again, so the AI actions leave that diary. An entry moved to another diary follows that diary's mode (deleting a diary moves its entries to the default diary). A third mode, **Ask each time** (`ask`, copied to `entries.diary_ai_ask`), is per-request consent: the journal-wide features leave the diary out exactly as they do one with AI off (the same `aiReadableEntrySql()`/`AI_READABLE_WHERE`, auto-tagging on save, and a book's AI weaving, `400 BOOK_AI_DIARY_OFF`), and every request about one of its entries or its text is refused with `403 DIARY_AI_CONSENT_REQUIRED` unless it carries `aiConsent: true` (`POST /api/ai/summarize`, `/api/ai/chat`, `/api/ai/fix-writing` and `/api/ai/suggest-tags` naming the diary, `POST /api/attachments/{id}/transcribe` for an entry's recording or one naming the diary, `POST /api/memoir/follow-ups` for a memoir diary that asks), checked before the provider is called (`assertEntryAiAllowed(entry, consent)`, `assertDiaryAiAllowed(diary, consent)`, `AiDiaryGateService.assertTextAiAllowed(userId, diaryId, consent)`). The web app sends `aiConsent` only after the writer confirmed the dialog showing exactly what goes out and to which provider and model (the text and what goes with it; for an entry chat, the entry and the whole conversation, asked again for each message; for a transcription, the recording's name and length, asked before a memoir recording is even uploaded); so it is enforced by the server for every request that names the diary or the entry, while the consent itself, like the diary a text names, is the client's word. Like the PIN lock it is a gate, not encryption.
- Every prompt treats journal text as untrusted data: it is wrapped in tagged blocks (`ai/untrusted-content.ts`, which escapes a closing tag inside the text) and the system prompt tells the model to ignore instructions inside them. New prompts must use the same helper.
- The entry chat's system prompt, and that of **Discuss these entries** (`ai/entries-chat.ts`), carry `COMPANION_SAFETY_INSTRUCTIONS` (`ai/companion-safety.ts`): the companion never acts as a therapist, and on signs of suicide, self-harm or danger it stops analyzing and sends the writer to a crisis line, emergency services or someone they trust, without giving phone numbers (the web app lists vetted ones itself). The web app's crisis check (`utils/crisisSignals.ts`) runs in the browser only and sends nothing.
- Mood readings with clinical labels are discarded, and so is a weekly reflection whose summary or question uses one (a theme that does is dropped), as is a memoir follow-up question that does. Applying a tag plan does not call the provider again.
- Usage rows store metadata only (model, tokens, cost, time), never prompts or completions.

## Container Images

The production PostgreSQL client image (setup hook and backup CronJob, see [Deployment](./deployment.md#production-desired-state)) is `postgres:18.6-alpine3.24@sha256:10a5c69a83035ab5239f5620d708520e8b28f5aa1f2b20143e6024532edadfb5`, built 2026-10-21. It replaced `18.6-bookworm`, whose Debian 12 packages carry critical findings with no Debian fix (zlib minizip CVE-2023-45853, SQLite CVE-2025-7458, libxml2 CVE-2026-6653) and a Perl finding (CVE-2026-9538); `18.6-trixie` still has the libxml2 one. The Alpine image has no Perl, and its zlib and libxml2 are not affected.

Trivy 0.74.0 (database of 2026-10-26, `--severity CRITICAL,HIGH`, amd64 and arm64) found in it:

- Alpine packages: no critical findings; two high ones fixed in newer Alpine packages (brotli-libs CVE-2026-111497, libcurl CVE-2026-92392), which the next upstream rebuild picks up. Neither the setup hook nor `pg_dump` uses brotli or curl.
- `/usr/local/bin/gosu` (the official image's entrypoint helper, gosu 1.19 built with Go 1.24.6): one critical Go standard library finding (CVE-2025-68121, `crypto/tls` session resumption) and 24 high ones, fixed in newer Go releases. Every official `postgres` variant ships the same binary. Both jobs replace the entrypoint with `/bin/sh` and run as UID 65534, so gosu never runs. Accepted as an exception below.

**Accepted exception: `gosu` in the PostgreSQL client image, until 2027-02-23** (the owner's decision of 2026-11-23).

- *What:* CVE-2025-68121 (critical) and the 24 high Go standard library findings in `/usr/local/bin/gosu` of `postgres:18.6-alpine3.24@sha256:10a5c69a8303…`, used only by the database setup Job and the `postgres-backup` CronJob. Nothing else in the image is accepted: a critical finding in any other package or binary is not covered.
- *Why it is not reachable:* gosu is the official image's entrypoint helper for dropping from root to the `postgres` user. Both jobs set `command: ["/bin/sh", …]`, so the image's entrypoint (and with it gosu) is never started; they run as UID 65534 with `runAsNonRoot`, so gosu could not switch users even if called; and the vulnerable code is Go's `crypto/tls`, while gosu opens no network connection at all. The jobs' own network use in this image (`psql` and `pg_dump`) is PostgreSQL's libpq, not Go's; the backup's S3 upload runs in a separate `aws-cli` container.
- *Recheck:* at each upstream rebuild of the `18.6-alpine3.24` tag (or the next PostgreSQL 18 minor), and in any case before 2027-02-23, scan the new index digest as below. Move to it when its gosu is built with a fixed Go and has no other critical finding, then remove this exception. If the deadline passes with no fixed upstream image, decide again before then between renewing the exception and a helper image built `FROM` this one without gosu. A change that makes either job run the entrypoint, run as root or call gosu ends the exception at once.

Recheck before moving the digest: `trivy image --severity CRITICAL,HIGH --platform linux/amd64 docker.io/library/postgres:<tag>@<index digest>` (and `linux/arm64`), or the platform's Grafana **Trivy Security Reports** dashboard. `mirror.gcr.io/library/postgres@<index digest>` serves the same content when Docker Hub's anonymous pull limit is reached.

## npm Dependencies

`npm audit` reports no findings in the repository root or in `thoughty-web` (2026-11-23). In `thoughty-server` it reports four moderate findings, two advisories that only a major upgrade fixes: `glob` 9 to 14.0.1 (GHSA-3g3m-2fjr-6pw4, fixed in 14) and `minimatch` 7 to 11.0.0 (GHSA-g3hv-75wg-m249, fixed in 11). They come in through the Nest CLI 11, build tooling only, which pins `glob` 13.0.6 (with `minimatch` 10) and moves past it in 12, and through TypeORM 0.3.31, which expands the entity and migration paths of `src/database/data-source.ts` with `glob` 10 and `minimatch` 9 and is fixed only in 1.x. Those patterns are fixed in the code and never come from a request. typescript-eslint 8.73.0, whose `typescript-estree` takes `minimatch` 11, cleared the same `minimatch` finding from the lint tooling of both apps. Run it in all three after changing dependencies. Fixed versions are taken within each package's current major; a major upgrade is taken only when its breaking changes do not reach this code base, as with `nodemailer` 10, whose only break is requiring Node.js 20 (the images run 26) and which ships its own types, so `@types/nodemailer` is gone. Remove such an override once the dependency itself moves past the fix, as `@nestjs/swagger` 11.4.8 did for its `js-yaml` pin (5.5.0, past GHSA-r3ph-w7gj-g6xm).

## Review Checklist

Runtime hardening and scanning are in [Deployment](./deployment.md#delivery-pipeline). For security-sensitive changes, check:

- Does it add a public route, and is its throttle right?
- Does it expose journal data, attachments, settings, or credentials to anyone but the owner?
- Is every query scoped to the user, including referenced diaries and entries?
- Does it send journal content to a third party, and is it in the AI table?
- Does it need a larger body limit or a new upload path?
- Does it add a secret, and how is it rotated?
- Does it change security assumptions enough to need an ADR?
